# Tenant P1.3 qualification lab

Это исходный план квалификации P1.3. Упоминания будущих implementation/lock files и `not-run` ниже фиксируют состояние того этапа. Текущие команды разработки и границы их покрытия описаны в [README](../../README.md); успешный локальный запуск не обновляет исторические acceptance manifests автоматически. Новые лабораторные запуски должны использовать отдельные disposable ресурсы и сохранять собственные результаты.

`python3 -I -m venv .venv-contracts` и `.venv-contracts/bin/python -I -m pip install --require-hashes -r tools/contract-requirements.lock` воспроизводят инструмент на CPython 3.12/Linux x86_64. Lock содержит hash конкретного wheel `rpds-py` этой платформы; на другой платформе нужен отдельный явно проверенный lock, а не отключение `--require-hashes`. Запуски: `.venv-contracts/bin/python -I scripts/check-contract-fixtures.py --all` и `.venv-contracts/bin/python -I -m unittest discover -s tests -p test_contract_fixtures.py`. Для ledger: `--results <file> --item Pn.m [--profile <id>] --evidence-root <root>`; `@plan/` определяется относительно указанного evidence root. Нужны все portions выбранного item/profile, включая not-run. Для wire: `--context <file> --registry <file>` с host-owned JSON `{"namespaces":["..."],"extensions":{"vendor:type":{"version":1,"refs":["field"]}}}`. Валидация wire не подтверждает trusted origin, admission или фактический binding. Изменение frozen corpus требует явного contract diff и обновления pinned hash в validator с повторением всех затронутых проверок. Проверка ledger связывает запись с portion, candidate и непустым raw файлом, но не доказывает истинность его содержимого.

Точная матрица будущей qualification: PHP 8.4/Laravel 12 для Vaulter; PHP 8.4/Laravel 13 для CoreX/Vaulter; PHP 8.5/Laravel 13 для actual FlexCRM (входной manifest ^13.7, наблюдавшийся lock 13.31.0); core smoke PHP 8.4 и 8.5. PG 16 и инструменты pg_dump/pg_restore 16, Redis 7; file и Redis sessions, local storage, sync и central database queue. Для каждой lane отдельные зафиксированные Composer lock и fresh install в disposable каталоге из packaged artifacts, без path symlink на source. Lock-файлы runtime пока не существуют; создание и фактическая квалификация относятся к будущим items. Не выполнять Composer update рабочего FlexCRM.

Перед каждой будущей lab-сессией исполнитель создаёт случайный lowercase hex run ID и immutable run manifest; project/network/volumes называются `tenant_lab_<run-id>` с отдельными ресурсами PostgreSQL, Redis и archive. DB allowlist ровно `tenant_<run-id>_central_test`, `tenant_<run-id>_a_test`, `tenant_<run-id>_b_test`, `tenant_<run-id>_template_test`, `tenant_<run-id>_clone_test`; длину run ID ограничить так, чтобы итоговое имя помещалось в PostgreSQL identifier limit. Явные роли `tenant_<run-id>_admin` и `tenant_<run-id>_runtime`: admin DSN только DDL harness; runtime DSN только restricted runtime role, не superuser/createdb; отдельные DSN для каждой DB. Все credentials одноразовые, не выводятся в logs и не берутся из рабочего environment. Только создаваемые из manifest disposable network/volumes, без bind mounts с working data и без работающих очередей. Никакие команды этого runbook не нацелены на существующие DSN.

Preflight до каждого потенциального DDL/restore и повторно непосредственно перед effect: по manifest сверить Compose project, container ID, network, volume IDs и PG system identifier с явно зафиксированным allowlist конкретного запуска; проверить PostgreSQL 16/Redis 7 и изолированность; проверить exact DB/role в manifest, `_test` suffix, текущие server/database/user, права runtime user и schema owner; проверить, что archive относится к этому же run ID. Несовпадение, отсутствие факта или неизвестный target означает fail closed до effect. После unknown outcome ресурс изолировать и сверить durable receipt/catalog; не повторять DDL и не удалять его по похожему имени. Уборка только точных ID из run manifest после сохранения evidence; quarantine исключается из автоматической уборки.

Будущие fault cases требуют реальных процессов и durable evidence: два независимых PHP процесса соревнуются за один ключ; kill connection/process после claim, CREATE, archive write, DROP и до metadata commit, отдельно потерять response после успешного effect. После каждого сбоя сверить исходные operation ID/receipt, target, catalog и число физических effects; повтор выдаёт original receipt или явный reconcile, без второго writer. Отдельно проверить partial activation/reverse journal, исчезновение или новую incarnation предыдущего binding, stale held service и deferred dispatch. Для restore/clone создать backups metadata и очереди разных возрастов, вернуть старые UUID/DB names и попытаться использовать старую очередь после смены incarnation; до reopen нужен внешний recovery anchor, без него отказ fail closed. Archive другого resource с корректным checksum отвергается; отсутствие writer/verifier останавливает операцию до DROP.

Worker protocol: изолированный supervisor запускает настоящий worker; после poison или утечки stream enqueue отдельный идентифицируемый sentinel job, наблюдать реальное завершение worker и отсутствие sentinel effect/ACK; собрать PID/exit, supervisor log, queue/job IDs и durable state. Проверить fresh worker отдельно, не подменять остановку сравнением DTO. Будущие HTTP, direct SQL, retained handles, session, storage, queue, race, DDL, backup и consumer installation проверки здесь **not-run**; их точные команды определяются после появления implementation и isolated lab. Synthetic lab policy не устанавливает business retention/replay/legal policy.
